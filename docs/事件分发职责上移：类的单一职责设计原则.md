# 事件分发职责上移：类的单一职责设计原则

本文说明为什么要把事件分发从 `EpollPoller` 移到 `EventLoop`，以及这次调整如何改善 Reactor 的职责边界。

# Situation — 情境

重构前，`EpollPoller::poll()` 同时负责：

- 调用 `epoll_wait` 等待事件；
- 把就绪事件转换为 `Channel` 列表；
- 直接调用 `Channel::handle_events()` 分发事件；
- 调整内部容量。

这样底层的 epoll 封装不仅提供事件，还决定了事件如何被处理，导致机制和调度策略耦合。

# Task — 任务

需要重新划分职责：

1. `EpollPoller` 只负责 epoll 的等待、注册和就绪事件收集；
2. `EventLoop` 负责 Reactor 主循环和事件分发；
3. 主流程应能直接表现为“poll → dispatch → pending functors”；
4. 为后续优先级分发或批量策略保留扩展位置。

# Action — 重构方案

### 接口调整

将 `EpollPoller::poll()` 从只产生副作用改为返回活跃 `Channel` 列表：

```cpp
auto activeChannels = poller_->poll(timeoutMs);
for (Channel* channel : activeChannels) {
    channel->handle_events();
}
do_pending_functors();
```

此后，`EpollPoller` 不再依赖 `Channel::handle_events()`，只返回底层观察到的结果。

### 重构前后的职责

| 组件 | 重构前 | 重构后 |
| :--- | :--- | :--- |
| `EpollPoller` | 等待、收集、分发、容量管理 | 等待、收集、容量管理 |
| `EventLoop` | 调用 Poller | 获取事件、分发事件、执行待处理任务 |
| `Channel` | 处理自身事件 | 处理自身事件 |

`EventLoop` 作为相邻组件之间的协调者，负责把底层机制产生的事件交给上层对象。

### 设计原则

- **单一职责**：Poller 只表达“哪些 fd 就绪”，不决定“如何处理”；
- **机制与策略分离**：epoll 是机制，事件分发顺序是 Reactor 策略；
- **相邻通信**：`EventLoop` 同时持有 Poller 和活跃 Channel，由它完成两者之间的协调。

# Result — 结果

- `EpollPoller::poll()` 的返回值语义更清晰，副作用更少；
- `EventLoop::loop()` 成为完整可读的 Reactor 主流程；
- 底层 Poller 不再依赖上层 Channel，耦合降低；
- 将来调整分发优先级时，只需要修改 EventLoop。

# 核心设计要点提炼

| 设计点 | 说明 |
| :--- | :--- |
| 职责上移 | 事件分发属于 Reactor 调度策略，应由 `EventLoop` 负责。 |
| Poller 边界 | `EpollPoller` 只提供就绪事件，不调用业务对象。 |
| 主流程 | `poll → dispatch → do_pending_functors`。 |
| 可扩展性 | 分发顺序和批处理策略可以独立演进。 |

# 面试核心问答总结

## Q1：为什么不让 EpollPoller 直接分发 Channel？

因为 Poller 是 epoll 的机制封装，不应该依赖上层 Channel 的处理接口。直接分发会把底层机制和上层策略耦合在一起。

## Q2：为什么由 EventLoop 负责分发？

EventLoop 是 Reactor 的调度中心，既能拿到 Poller 返回的活跃列表，也能决定事件分发顺序和待处理任务的执行时机。

## Q3：返回 vector 会不会产生性能损耗？

返回的是指针列表，通常可以通过移动或返回值优化避免不必要的拷贝。相比职责边界变清晰带来的可维护性收益，这个开销是可接受的。
