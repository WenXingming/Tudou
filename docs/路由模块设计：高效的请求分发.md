# HTTP Router 设计与实现

`HttpRouter` 负责把解析完成的 `HttpRequest` 分发给对应的业务处理器。它将协议解析和业务路由解耦，并按“精确匹配 → 405 判定 → 前缀兜底 → 404 回退”的顺序处理请求。

# Situation — 项目背景

Tudou 已经使用 Reactor 处理网络 I/O，并通过 `llhttp` 将字节流解析为结构化的 `HttpRequest`。

随着 `FileLinkServer`、`StarMindServer` 等业务增加，HTTP 请求路径和方法越来越多。如果把分发逻辑直接写在 `HttpServer::on_http_request()` 中，代码会逐渐变成大量 `if-else`，网络层也会和具体业务产生耦合。

因此，需要一个独立的路由模块，专门负责“请求应该交给哪个处理器”。

# Task — 任务目标

Router 需要满足以下要求：

1. 将 HTTP 解析和业务分发分开；
2. 支持按 `Method + Path` 的精确路由；
3. 支持静态资源和动态路径所需的前缀路由；
4. 能区分 `404 Not Found` 和 `405 Method Not Allowed`；
5. 在每个请求的关键路径上保持较低的查找开销；
6. 让业务方可以通过清晰的接口注册处理器。

# Action — 技术方案与实现

### 路由分发顺序

Router 固定按照以下顺序处理请求：

```text
精确路由匹配
    ↓ 未命中
检查路径是否注册过其他方法
    ↓ 路径存在
返回 405 + Allow
    ↓ 路径不存在
按注册顺序扫描前缀路由
    ↓ 仍未命中
返回 404
```

精确路由必须优先于前缀路由，否则前缀规则可能提前接管一个本应由明确 API 处理的请求。

核心分发逻辑如下：

```cpp
DispatchResult HttpRouter::dispatch(
    const HttpRequest& req, HttpResponse& resp) const {
    const Handler* exactHandler = find_exact_handler(req);
    if (exactHandler != nullptr) {
        (*exactHandler)(req, resp);
        return DispatchResult::Matched;
    }

    const AllowedMethods* allowedMethods =
        find_allowed_methods(req.get_path());
    if (allowedMethods != nullptr) {
        write_method_not_allowed_response(req, *allowedMethods, resp);
        return DispatchResult::MethodNotAllowed;
    }

    const Handler* prefixHandler = find_prefix_handler(req.get_path());
    if (prefixHandler != nullptr) {
        (*prefixHandler)(req, resp);
        return DispatchResult::Matched;
    }

    write_not_found_response(req, resp);
    return DispatchResult::NotFound;
}
```

### 精确路由：`Method + Path` 哈希查找

精确路由使用 `RouteKey` 同时保存 HTTP 方法和路径：

```cpp
struct RouteKey {
    std::string method;
    std::string path;

    bool operator==(const RouteKey& other) const {
        return method == other.method && path == other.path;
    }
};
```

路由表使用 `std::unordered_map<RouteKey, Handler, RouteKeyHash>`。注册 `GET /login` 和 `POST /login` 时，它们是两个不同的路由。

平均情况下，精确路由可以在 `O(1)` 时间内完成查找，适合请求量较大的常规 API。

### 405 判定：单独维护允许方法索引

只根据 `(Method, Path)` 查找无法区分以下两种情况：

- 路径根本没有注册：应该返回 `404`；
- 路径存在，但当前方法没有注册：应该返回 `405`。

因此，Router 额外维护 `Path -> AllowedMethods` 索引。注册路由时同时更新两张表：

```cpp
void HttpRouter::add_route(
    const std::string& method,
    const std::string& path,
    Handler handler) {
    exactRoutes_[RouteKey{method, path}] = std::move(handler);
    allowedMethodsByPath_[path].insert(method);
}
```

当路径存在但方法不允许时，返回 `405 Method Not Allowed`，并设置 `Allow` 响应头，例如：

```text
Allow: GET, POST
```

这样客户端可以知道该路径支持哪些方法，Router 也能严格区分 404 和 405。

### 前缀路由：按注册顺序兜底

前缀路由用于处理静态资源或动态路径，例如：

```text
/static/
/file/
```

前缀路由使用 `std::vector` 保存，并按注册顺序线性扫描：

```cpp
void HttpRouter::add_prefix_route(
    const std::string& prefix,
    Handler handler) {
    prefixRoutes_.push_back(PrefixRoute{prefix, std::move(handler)});
}
```

选择 `vector` 是因为注册顺序本身就是优先级。它的查找复杂度为 `O(n)`，但前缀路由通常属于兜底分支，不会影响精确 API 的主要路径。

### 注册接口与职责边界

Router 对外提供语义清晰的注册接口：

```cpp
router.add_get_route("/login", loginHandler);
router.add_post_route("/login", loginHandler);
router.add_prefix_route("/static/", staticFileHandler);
```

`HttpServer` 只负责接收并解析请求，再把请求交给 Router；业务模块只需要在初始化阶段注册自己的处理器。这样新增 API 不需要修改核心分发逻辑。

# Result — 重构效果

- `HttpServer` 不再直接包含业务分发的 `if-else`；
- HTTP 解析、路由匹配和业务处理职责清晰分离；
- 精确 API 使用哈希表快速查找；
- 通过路径索引正确区分 404 和 405，并生成 `Allow` 头；
- 前缀路由可以处理静态资源和动态路径；
- 新增 API 主要通过注册路由完成，不需要修改 Router 的分发流程。

# 核心设计要点提炼 (Key Architectural Points)

| 设计点 | 说明 |
| :--- | :--- |
| 职责分离 | `HttpServer` 负责接收请求，`HttpRouter` 负责路由，业务处理器负责具体业务。 |
| 精确匹配 | 使用 `Method + Path` 作为联合键，通过 `unordered_map` 快速查找。 |
| 405 语义 | 额外维护路径到允许方法的索引，区分 404 和 405。 |
| 前缀兜底 | 使用 `vector` 保存前缀路由，注册顺序决定匹配优先级。 |
| 固定分发顺序 | 精确匹配 → 405 判定 → 前缀兜底 → 404。 |

# 面试核心问答总结 (Q&A)

## Q1：为什么要设计独立的 Router？

因为 HTTP 解析和业务分发是两种不同职责。独立 Router 可以避免 `HttpServer` 里堆积大量业务判断，也方便业务模块集中注册路由。

## Q2：为什么精确路由使用 `Method + Path` 作为联合键？

同一路径可以对应多个 HTTP 方法，例如 `GET /login` 和 `POST /login`。把方法和路径放在同一个键中，可以直接定位唯一处理器，平均查找复杂度为 `O(1)`。

## Q3：为什么需要额外的路径索引来处理 405？

精确路由查找失败时，单靠哈希表无法知道是“路径不存在”还是“方法不允许”。额外的 `Path -> AllowedMethods` 索引可以区分两种情况，并生成正确的 `Allow` 响应头。

## Q4：为什么前缀路由使用 `vector`，而不是继续使用哈希表？

前缀匹配不是完整字符串匹配，通常需要遍历候选前缀。而且前缀路由的注册顺序代表优先级，`vector` 能自然保留这个顺序。它只用于兜底分支，`O(n)` 的成本是可接受的。
