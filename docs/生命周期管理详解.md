# 生命周期管理设计：从所有权、RAII 到回调安全

Tudou 的生命周期管理不仅是防止内存泄漏，还要同时回答：谁拥有对象、谁只是访问、回调期间如何保活、资源由谁释放，以及操作应该在哪个线程执行。

# Situation — 为什么需要生命周期管理

Reactor 中最危险的情况不是对象没人释放，而是对象在回调尚未返回时被提前释放：

```text
Channel::handle_events
  → close callback
  → TcpServer::remove_connection
  → 连接表 erase
  → TcpConnection / Channel 析构
  → 当前 Channel 栈帧继续访问已释放对象
```

多线程还会增加另一类风险：对象虽然仍然存活，但错误线程同时修改它的 buffer、Channel 或 fd。

因此，`shared_ptr` 只能解决“对象是否存活”，不能自动解决线程安全和资源归属。

# Task — 设计目标

生命周期方案需要同时保证：

1. 所有权边界清晰；
2. 回调期间不会 Use-After-Free；
3. fd、epoll 注册关系和对象按正确顺序释放；
4. 跨线程操作回到 owner loop；
5. 不把所有访问都变成昂贵的共享所有权。

# Action — Tudou 的实现

### 四种指针语义

| 类型 | 是否拥有 | 典型用途 |
| :--- | :--- | :--- |
| `T*` / `T&` | 否 | Poller 借用 `Channel` |
| `unique_ptr<T>` | 是，独占 | `EventLoop` 持有 Poller、TimerQueue |
| `shared_ptr<T>` | 是，共享 | `TcpConnection`、跨线程任务 |
| `weak_ptr<T>` | 否，观察 | `Channel::tie_`，避免长期拥有 |

原则是：所有权用强语义表达，临时访问尽量使用引用或裸指针。

### 当前主要所有权边界

| 对象 | owner | 说明 |
| :--- | :--- | :--- |
| `Acceptor` | `TcpServer` 的 `unique_ptr` | 服务器拥有监听器 |
| `EpollPoller` / `TimerQueue` | 所属 `EventLoop` | loop 私有资源 |
| `Channel` | `TcpConnection` | 连接拥有事件通道 |
| socket fd | `TcpConnection::Socket` | RAII 负责最终 `close` |
| `TcpConnection` | `shared_ptr` 连接表、回调和任务 | 多方需要临时或长期持有 |
| Poller 中的 `Channel*` | 借用 | 不负责销毁 |

`Channel` 负责事件注册和回调分发，`Socket` 负责 fd 生命周期，职责不混在一起。

### RAII 与析构顺序

如果 `TcpConnection` 的成员声明为：

```cpp
Socket connSocket_;
std::unique_ptr<Channel> channel_;
```

C++ 会按声明逆序析构：先销毁 `channel_`，再销毁 `connSocket_`。因此先注销 epoll 事件，再关闭 fd，避免 Poller 继续引用已关闭的 fd。

### shared_ptr 与回调保活

`TcpConnection` 需要被连接表、回调参数和跨线程 Lambda 共同使用，因此适合由 `shared_ptr` 管理。

关闭回调中需要局部强引用：

```cpp
void TcpConnection::handle_close_callback() {
    auto guardThis = shared_from_this();
    closeCallback_(guardThis);
}
```

即使回调内部从连接表删除最后一个外部引用，`guardThis` 也能保证当前调用栈结束前对象仍然有效。

跨线程发送也要捕获 `shared_ptr`：

```cpp
auto self = shared_from_this();
loop_->queue_in_loop([self, msg] {
    self->send_in_loop(msg);
});
```

### Channel tie

Channel 平时保存 `weak_ptr<void>`，进入事件分发时才 `lock()` 成临时 `shared_ptr`。这样可以：

- 回调期间保活 owner；
- 不让 Channel 长期拥有 TcpConnection；
- 不让底层 Channel 依赖上层具体类型；
- owner 已销毁时安全跳过事件。

### 线程归属

对象存活不等于可以任意线程访问。连接的 buffer、Channel 和 EventLoop 私有资源必须回到 owner loop：

```text
其他线程调用 send
  → queue_in_loop
  → eventfd 唤醒 owner loop
  → owner loop 修改连接状态
```

# Result — 结果

- 对象、fd、epoll 注册关系的 owner 清晰；
- 回调和异步任务有明确的临时保活机制；
- Channel tie 防止事件分发期间 owner 提前析构；
- RAII 成员顺序保证先注销事件、后关闭 fd；
- 线程归属与生命周期管理相互配合，而不是只依赖 `shared_ptr`。

# 核心设计要点提炼

| 设计点 | 说明 |
| :--- | :--- |
| 所有权 | 用 `unique_ptr`、`shared_ptr` 和 RAII 明确谁负责销毁。 |
| 借用 | Poller 等非 owner 只保存裸指针或引用。 |
| 回调保活 | 用局部 `shared_ptr` guard 覆盖整个回调。 |
| tie | `weak_ptr` 平时观察，回调时临时升级。 |
| 线程边界 | 活着的对象也必须在正确 owner loop 中访问。 |

# 面试核心问答总结

## Q1：shared_ptr 能解决所有生命周期问题吗？

不能。它只能保证对象在引用存在时不析构，不能解决错误线程访问、fd 注册顺序或回调重入问题。

## Q2：为什么 Channel 不直接持有 TcpConnection 的 shared_ptr？

长期强引用会破坏分层并影响正常析构。Channel 只需在事件回调期间临时保活，因此使用 tie。

## Q3：为什么 fd 不由 Channel 关闭？

Channel 管理事件注册，Socket 通过 RAII 管理 fd。职责分离后可以明确先注销 epoll，再关闭 fd。

## Q4：为什么跨线程任务要捕获 shared_ptr？

任务是异步执行的，调用方返回后连接可能被关闭。捕获 `shared_ptr` 可以保证任务执行期间对象仍然存在。
