# 心跳检测设计：三层防御体系与失活连接清理

Tudou 使用内核探活和用户态空闲检测共同识别失活连接，并把关闭流程统一交给连接生命周期管理。业务协议如果有更高要求，还可以在上层增加主动 Ping/Pong。

# Situation — 情境

连接可能因为拔网线、路由器故障、对端进程崩溃或应用假死而长期占用 fd 和内存。慢速客户端还可能故意保持连接但很少发送数据。

TCP Keep-alive 只能说明对端内核仍能回复探测包。如果对端应用已经死锁，但操作系统还活着，内核探活仍可能认为连接正常。因此，单独依赖 Keep-alive 不够。

# Task — 任务

探活设计需要覆盖不同层次的问题：

1. 发现网络链路和对端系统已经失效；
2. 发现连接长期没有用户态数据；
3. 为需要双向确认的业务协议预留主动心跳；
4. 连接失活后统一释放 `TcpConnection`、上下文和 Socket fd。

# Action — 设计与实现

### 三层防御

| 层级 | 机制 | 检测对象 |
| :--- | :--- | :--- |
| L4 | TCP Keep-alive | 链路和对端操作系统是否仍然可达 |
| L4/L7 | `ConnectionHeartbeat` | 用户态连接是否持续收到入站数据 |
| L7 | 业务 Ping/Pong（当前未实现） | 协议处理路径和业务响应是否健康 |

### 第一层：TCP Keep-alive

`TcpConnection` 创建时开启 keep-alive，由内核周期性发送探测包。多次探测没有收到 ACK 时，内核报告连接异常。

它能覆盖断网、拔网线和对端 OS 崩溃，但无法识别“对端 OS 正常、应用已经卡死”的情况。

### 第二层：用户态空闲检测

`ConnectionHeartbeat` 通过 `refresh()` 记录最后一次用户态活跃时间。当前实现只在 `TcpConnection::on_read` 成功读到数据并把数据交给上层时刷新。

定时器检查超时后调用 `force_close()`。因此，内核仍能回复 ACK、但长期没有业务数据到达的连接，也能被清理。

### 第三层：业务主动心跳

长连接 RPC、WebSocket 等协议可以自行发送 Ping 并等待 Pong，用于确认协议处理路径和测量 RTT。该机制与具体协议强相关，当前留在业务层实现；HTTP/1.1 更适合使用请求 deadline 等机制。

### 失活后的关闭路径

不论失活由哪一层发现，最终都应收敛到统一关闭流程：

```text
探活或空闲检查发现异常
  → force_close / close_connection
  → TcpServer::remove_connection
  → 从 connections_ 中移除 shared_ptr
  → TcpConnection 和上下文析构
  → RAII Socket 关闭 fd
```

事件循环可能先收到 `EPOLLIN`、`EPOLLERR` 或 `EPOLLHUP`，读取结果可能是 EOF 或非 `EAGAIN` 错误；这些情况最终都进入 `close_connection()`。

# Result — 结果

- Keep-alive 负责链路层探活；
- `ConnectionHeartbeat` 补充用户态空闲检测；
- 业务层可以按协议需要增加主动心跳；
- 失活连接通过统一关闭路径释放对象和 fd；
- 探活机制与具体业务协议保持相对独立。

# 核心设计要点提炼

| 设计点 | 说明 |
| :--- | :--- |
| 分层探活 | 内核、网络库、业务协议分别处理不同层次的问题。 |
| 空闲检测 | 关注是否有数据真正到达用户态，而不是只看 TCP ACK。 |
| 统一关闭 | 所有失活原因最终进入同一条连接关闭和资源释放路径。 |
| 业务扩展 | L7 主动心跳按协议需要实现，不强行放进 TCP 层。 |

# 面试核心问答总结

## Q1：有 TCP Keep-alive，为什么还需要应用层检测？

Keep-alive 只能证明对端内核仍能回复 TCP 探测包，无法证明对端应用仍在处理业务。用户态空闲检测可以补充这一盲区。

## Q2：ConnectionHeartbeat 检测的是什么？

它检测一段时间内是否有入站字节真正到达用户态，而不是检测底层 TCP 是否还能回复 ACK。

## Q3：连接失活后如何保证资源释放？

统一进入 `close_connection()`，再由 `TcpServer` 移除连接表中的 `shared_ptr`，最后依靠 RAII 关闭 Socket fd。
