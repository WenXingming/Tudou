# 深入理解回调：为什么要用、它是什么、如何安全使用

回调就是：一个组件先注册一段逻辑，由另一个组件在合适的时机调用。它的核心是控制反转，不等同于异步，也不等同于继承关系。

# Situation — 为什么需要回调

网络事件发生的时间未知：连接可能随时建立，fd 可能随时可读，定时器可能随时到期。如果代码一直阻塞等待，就无法同时服务大量连接。

Reactor 的流程是：

```text
EventLoop 等待事件
  → Poller 返回就绪 fd
  → Channel 分发事件
  → TcpConnection 处理连接语义
  → 上层回调处理协议和业务
```

每一层只关心自己的职责：

- `Channel` 知道 fd 就绪，但不理解 HTTP；
- `TcpConnection` 知道收到了字节，但不决定业务；
- `HttpServer` 把请求交给 Router 和业务处理器。

回调让下层上报事件，而不必依赖上层具体类型。

# Task — 回调设计需要解决的问题

1. 让事件拥有者决定触发时机；
2. 让上下层保持松耦合；
3. 支持跨线程任务投递；
4. 明确回调对象的生命周期和线程归属；
5. 避免回调期间 owner 被提前销毁。

# Action — 回调的组成与使用

### C++ 中的回调

现代 C++ 通常用 `std::function` 保存可调用对象：

```cpp
class Channel {
public:
    using EventCallback = std::function<void(Channel&)>;

    void set_read_callback(EventCallback cb) {
        readCallback_ = std::move(cb);
    }

private:
    EventCallback readCallback_;
};
```

回调可以是普通函数、成员函数绑定、lambda 或其他函数对象。

一个完整的回调接口通常包含：

1. 回调类型；
2. 注册接口；
3. 成员变量；
4. 触发点。

### Tudou 的事件回调链

```cpp
channel_->set_read_callback(
    [this](Channel& ch) { on_read(ch); });
```

事件到来后：

```text
Channel
  → TcpConnection::on_read
  → TcpConnection::handle_message_callback
  → TcpServer::on_message
  → HttpServer::on_message
```

每层只调用相邻层的回调，避免底层直接依赖业务类型。

### 回调也可以表示跨线程任务

在 One-Loop-Per-Thread 模型中，其他线程不能直接修改连接状态，而是把操作封装为 lambda：

```cpp
void TcpConnection::send(const std::string& msg) {
    if (!loop_->is_in_loop_thread()) {
        auto self = shared_from_this();
        loop_->queue_in_loop([self, msg] {
            self->send_in_loop(msg);
        });
        return;
    }

    send_in_loop(msg);
}
```

这里的 lambda 也是回调：它把“未来要执行的动作”交给目标 EventLoop。

### 回调与依赖注入

回调是被注入的行为，依赖注入是把行为传给组件的方式。通过回调，组件依赖的是一个调用契约，而不是某个具体业务类。

### 回调期间的生命周期

回调可能触发关闭、从连接表移除对象，甚至导致 owner 析构。因此需要：

- 回调对象捕获 `shared_ptr` 时，明确是否真的需要保活；
- `Channel` 使用 tie 在事件分发期间临时保活 owner；
- 跨线程任务捕获连接对象和数据副本；
- 所有修改操作回到 owner loop。

# Result — 结果

- EventLoop、Channel、TcpConnection 和业务层职责解耦；
- 事件触发时机由事件拥有者控制；
- 跨线程操作可以统一封装成任务投递；
- 回调链可以沿架构层次向上传递；
- 配合 `shared_ptr`、`weak_ptr` 和线程归属，避免回调期间的生命周期错误。

# 核心设计要点提炼

| 设计点 | 说明 |
| :--- | :--- |
| 定义 | 预先注册、由其他组件在未来触发的可调用逻辑。 |
| 控制反转 | 逻辑提供者不决定执行时机，事件拥有者决定。 |
| 分层通信 | 下层上报事件，上层处理语义，不直接依赖具体业务类。 |
| 跨线程 | lambda 把操作投递到正确的 EventLoop。 |
| 生命周期 | 回调可能改变对象状态，必须明确保活和线程边界。 |

# 面试核心问答总结

## Q1：回调和异步是一个概念吗？

不是。回调可以同步执行，也可以异步执行；异步只是常见使用场景。

## Q2：为什么 Reactor 大量使用回调？

事件发生时间未知，EventLoop 和 Channel 负责等待与分发，业务逻辑通过回调在事件发生后执行。

## Q3：回调和继承有什么关系？

回调通常是组合关系中的行为注入，不要求继承。下层只保存调用契约，不需要知道上层具体类型。

## Q4：设计回调时最容易忽略什么？

回调期间的 owner 生命周期、回调执行线程、异步数据的有效期，以及回调重入导致的状态变化。
