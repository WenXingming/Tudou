# 阻塞 IO 与非阻塞 IO 详解

阻塞/非阻塞描述的是一次 I/O 系统调用在条件不满足时的行为。它和同步/异步、I/O 多路复用是三个不同维度，面试时需要先分开。

# Situation — 三个概念

### 阻塞与非阻塞

当 `read`、`write`、`accept` 或 `connect` 暂时不能完成时：

- 阻塞 fd：调用线程睡眠等待；
- 非阻塞 fd：立即返回，常见错误是 `EAGAIN`、`EWOULDBLOCK` 或 `EINPROGRESS`。

严格来说，描述的是“某个 fd 上的某次 I/O 调用”，而不是抽象地说 socket 本身好或坏。

### 同步与异步

同步 I/O 中，应用发起 `read` / `write`，并由调用者负责处理数据结果；异步 I/O 则由内核或运行时完成操作后通知应用。

`epoll` 不是异步 I/O。常见的 `epoll + O_NONBLOCK` 模型是：

```text
同步 I/O + 非阻塞 fd + I/O 多路复用
```

### I/O 多路复用

`select`、`poll` 和 `epoll` 只负责同时监视多个 fd 的就绪状态，不替应用执行真正的 `read`、`write` 或 `accept`。

# Task — 需要解决的问题

网络库需要选择合适的 I/O 行为：

1. 不让一个慢连接阻塞整个事件循环；
2. 正确处理短读、短写和 `EAGAIN`；
3. 用一个线程管理多个连接；
4. 在简单场景下保留阻塞 I/O 的可读性优势。

# Action — 工作方式与工程取舍

### `read` 和 `write` 的基本行为

对流式 socket：

- `read` 从内核接收缓冲区拷贝到用户缓冲区；
- `write` 把用户数据拷贝到内核发送缓冲区。

`read` 的结果：

- `> 0`：读到数据；
- `== 0`：对端关闭连接；
- `-1` 且 `EAGAIN`：当前没有数据。

`write` 也可能短写，即使 fd 是阻塞的，也不能假设一次写完全部数据。非阻塞写遇到发送缓冲区无空间时返回 `EAGAIN`，应用需要保存剩余数据。

### 阻塞 I/O

阻塞 I/O 的代码路径简单：

```text
调用 read / write
  → 条件不满足
  → 当前线程睡眠
  → 条件满足后返回
```

它适合连接数较少、每个线程只服务少量连接的程序，例如命令行工具、简单客户端和低并发服务。

问题是高并发时需要为大量“等待”分配线程，带来线程栈、上下文切换和慢连接占用等成本。

### 非阻塞 I/O

非阻塞 I/O 不会让调用线程睡眠：

```text
调用 read / write
  → 当前不能完成
  → 立即返回 EAGAIN
  → 处理其他任务
```

但单独使用非阻塞 I/O 会产生忙轮询：

```cpp
while (read(fd, buf, sizeof(buf)) < 0 && errno == EAGAIN) {
    // CPU 忙等，不应该这样做
}
```

高性能服务器通常采用：

```text
非阻塞 fd
  + epoll 等待就绪
  + 就绪后执行一次或有限次数 read / write
  + EAGAIN 时回到事件循环
```

### LT 与 ET 的实践边界

- LT（水平触发）：只要仍然可读或可写，下一次 `epoll_wait` 还会通知，代码更容易写对；
- ET（边沿触发）：只在状态从未就绪变为就绪时通知，通常需要循环读写直到 `EAGAIN`，否则可能丢失后续处理机会。

Tudou 使用非阻塞 socket 和 Reactor 事件循环，因此必须正确处理 `EAGAIN`、短读和短写，不能依赖一次系统调用完成全部工作。

# Result — 结果

- 明确区分了阻塞/非阻塞、同步/异步和 I/O 多路复用；
- 阻塞 I/O 保留了简单场景下的可读性；
- 非阻塞 I/O 避免慢连接阻塞事件循环；
- `epoll + O_NONBLOCK` 共同实现一个线程管理多个连接；
- 短读、短写和 `EAGAIN` 被视为正常控制流程，而不是异常。

# 核心设计要点提炼

| 设计点 | 说明 |
| :--- | :--- |
| 阻塞/非阻塞 | 描述 I/O 条件不满足时调用线程是否睡眠。 |
| 多路复用 | 只通知 fd 是否就绪，不负责真正读写。 |
| 非阻塞价值 | 防止一个连接阻塞整个 EventLoop。 |
| 正确组合 | 高并发场景使用 `O_NONBLOCK + epoll`。 |
| 结果处理 | 必须处理 `EAGAIN`、EOF、短读和短写。 |

# 面试核心问答总结

## Q1：epoll 是异步 I/O 吗？

不是。`epoll` 是 I/O 多路复用；Tudou 使用的是同步 I/O + 非阻塞 fd + 多路复用。

## Q2：为什么 epoll 已经通知可读，还要设置非阻塞？

就绪通知和真正读取之间可能发生状态变化，或者一次读取只消费部分数据。非阻塞可以保证事件循环不会因为一次 `read` 再次等待。

## Q3：非阻塞 I/O 为什么不能单独使用？

如果不断重试 `EAGAIN`，就会变成 CPU 忙轮询。需要让 `epoll` 负责等待状态变化。

## Q4：阻塞 I/O 一定更差吗？

不是。低并发、线程资源充足或逻辑以串行为主时，阻塞 I/O 更简单；高并发服务器才更需要非阻塞和多路复用。
