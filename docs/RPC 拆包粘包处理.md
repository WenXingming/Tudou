# Tudou RPC 协议分帧与拆包粘包设计

TCP 没有消息边界，RPC 必须在应用层定义帧格式。Tudou 的二进制 RPC 使用长度字段分帧，JSON-RPC 使用换行符分帧，两者都通过连接级缓冲处理半包和粘包。

# Situation — 情境

一次 TCP 读取可能只包含半个 RPC 请求，也可能包含多个请求。若直接按一次读取调用业务，会出现截断、拼接或数据错位。

# Task — 任务

需要为两种协议提供明确的分帧规则：

1. 能识别完整帧和半帧；
2. 解析失败时及时关闭异常连接；
3. 消费完整帧后继续处理后面的粘包；
4. 未消费数据保留到下一次读取；
5. 二进制字段跨平台传输时统一字节序。

# Action — 设计与实现

### Binary RPC：固定头部加长度字段

每个二进制帧包含 20 字节固定头部：

| 字段 | 长度 | 作用 |
| :--- | :--- | :--- |
| `magic` | 2 | 校验协议帧 |
| `version` | 1 | 协议版本 |
| `type` | 1 | 请求、响应或心跳类型 |
| `sequenceId` | 8 | 匹配一次调用 |
| `metaLen` | 4 | Meta 长度 |
| `bodyLen` | 4 | Body 长度 |

服务端为每条连接保存输入缓冲区，解码器按以下顺序判断：

```text
可读字节 < 20
  → HalfPack，等待完整头部

可读字节 < 20 + metaLen + bodyLen
  → HalfPack，等待完整负载

长度足够
  → 提取 Meta / Body，推进读指针，返回 Success
```

解码成功后继续循环，可以处理同一缓冲区中的下一个帧。魔数错误返回 `Error`，服务端关闭连接，避免异常输入持续占用缓存。

### JSON-RPC：换行符分帧

JSON-RPC 使用 `\n` 作为一条请求的结束标记：

```cpp
size_t pos = connBuf.find('\n');
if (pos == std::string::npos) {
    return; // 半包，等待后续数据
}

std::string request = connBuf.substr(0, pos);
connBuf.erase(0, pos + 1);
dispatch(request);
```

找不到换行符时保留整个缓存；找到后消费一行，并继续查找后面的请求。

### 网络字节序

二进制协议中的长度和 ID 使用大端网络字节序：

- 编码：`htobe16`、`htobe32`、`htobe64`；
- 解码：`be16toh`、`be32toh`、`be64toh`。

这样不同 CPU 架构的客户端和服务端可以使用同一帧格式。

# Result — 结果

- Binary RPC 使用长度字段准确分帧；
- JSON-RPC 使用换行符处理文本消息；
- 半包会保留到下一次读取，粘包会在循环中继续消费；
- 非法二进制帧会被及时拒绝；
- 数值字段使用统一网络字节序。

# 核心设计要点提炼

| 设计点 | 说明 |
| :--- | :--- |
| 二进制分帧 | 固定头部 + `metaLen` + `bodyLen`。 |
| 文本分帧 | 使用换行符作为 JSON-RPC 边界。 |
| 半包处理 | 不推进未完整帧的读指针，等待更多数据。 |
| 粘包处理 | 消费一帧后继续循环解析剩余数据。 |
| 跨平台 | 多字节整数统一使用大端网络字节序。 |

# 面试核心问答总结

## Q1：RPC 为什么必须自己做分帧？

TCP 只提供字节流，不提供消息边界。RPC 必须通过长度字段或分隔符确定一条消息的结束位置。

## Q2：半包时为什么不能删除已经读到的数据？

因为当前帧还不完整，删除数据会丢失头部或负载。应保留缓冲区，等后续字节到达后继续解析。

## Q3：二进制协议和 JSON-RPC 为什么采用不同分帧方式？

二进制协议适合固定头部和长度字段，解析高效；文本 JSON-RPC 使用换行符简单明确，便于调试和实现。
