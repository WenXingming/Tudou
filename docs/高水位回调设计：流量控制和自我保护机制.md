# 高水位回调：流量控制和自我保护机制

高水位回调用于监控 `TcpConnection` 的应用层写缓冲区，在慢客户端或网络拥堵时向业务层发出反压信号，避免单个连接无限积压数据。

# Situation — 情境

非阻塞 socket 在发送缓冲区暂时不可写时不会阻塞线程，待发送数据会进入 `TcpConnection::writeBuffer_`，等待后续可写事件继续发送。

如果对端读取很慢，而业务仍持续调用 `send()`，应用层缓冲区会不断增长，最终可能消耗过多内存，甚至导致 OOM。

# Task — 任务

需要提供一个简单的保护机制：

1. 设定单连接允许积压的数据上限；
2. 缓冲区首次越过上限时通知业务层；
3. 避免在持续高于阈值时重复触发回调；
4. 结合写完成通知，让业务在积压下降后恢复生产。

# Action — 设计与实现

### 边缘触发的高水位检测

`send()` 写入数据前后分别记录缓冲区长度，只在长度从阈值以下跨越到阈值及以上时触发回调：

```cpp
const size_t oldLen = writeBuffer_->readable_bytes();
writeBuffer_->write_to_buffer(msg);
const size_t newLen = writeBuffer_->readable_bytes();

if (highWaterMarkCallback_
    && oldLen < highWaterMark_
    && newLen >= highWaterMark_) {
    handle_high_water_mark_callback();
}
```

这种边缘触发方式避免了缓冲区持续处于高水位时反复调用同一个回调。

### 与写完成回调配合

高水位回调只负责通知，不直接替业务决定如何限流。业务可以：

- 暂停继续生产数据；
- 暂停读取新的上游任务；
- 关闭或限制异常积压的连接。

当写缓冲区逐渐排空时，通过 `WriteCompleteCallback` 通知业务恢复生产，形成反压闭环：

```text
写缓冲区越过高水位
  → 通知业务暂停生产
  → socket 可写，缓冲区逐步下降
  → 写完成回调
  → 业务恢复生产
```

# Result — 结果

- 业务能够感知单连接的发送积压；
- 慢客户端不会无边界地占用应用层内存；
- 回调采用边缘触发，不会在高水位状态下重复调用；
- 高水位和写完成回调共同提供了可控的反压机制。

# 核心设计要点提炼

| 设计点 | 说明 |
| :--- | :--- |
| 保护对象 | `TcpConnection` 的应用层 `writeBuffer_`。 |
| 触发条件 | 写入前低于阈值，写入后达到或超过阈值。 |
| 触发方式 | 边缘触发，避免重复通知。 |
| 闭环 | 高水位通知暂停生产，写完成通知恢复生产。 |

# 面试核心问答总结

## Q1：为什么需要高水位回调？

非阻塞发送失败时，数据会积压在应用层写缓冲区。没有上限和通知机制，慢客户端可能持续消耗服务器内存。

## Q2：为什么不能每次 send 都触发回调？

缓冲区一旦超过阈值，后续每次发送都会满足条件，回调会被重复调用。只检测“跨越阈值”的瞬间可以避免这种噪声。

## Q3：高水位回调触发后如何恢复？

业务暂停继续生产数据，等待写缓冲区下降；当数据发送完成后，通过写完成回调恢复生产。
